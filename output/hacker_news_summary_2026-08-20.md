## 1. 科学研究揭示TikTok视频会抑制关键大脑认知区域的活动

**原文标题**: Scientific study reveals TikTok videos deactivate key cognitive brain regions

**原文链接**: [https://www.rathbiotaclan.com/tiktok-videos-deactivate-key-cognitive-brain-regions/](https://www.rathbiotaclan.com/tiktok-videos-deactivate-key-cognitive-brain-regions/)

最近一项科学研究发现，在TikTok和Instagram Reels等平台观看短视频会使参与认知控制的关键大脑区域失活。借助神经影像学技术，研究人员观察到，当参与者观看这些快速、由算法驱动的片段时，大脑的认知控制网络——负责注意力、规划和自我调节——活动减弱。与较长或更连续的视频格式相比，这种效应更为明显。

该研究表明，短视频快节奏、高度吸引人的特性可能鼓励被动观看，从而削弱一个人保持专注、延迟满足或抵抗习惯性刷屏的能力。研究人员指出，这可能对注意力持续时间、冲动控制甚至情绪产生影响，尤其是在重度使用的情况下。不过，他们也指出，还需要更多研究来确定这些大脑变化是暂时的，还是会对认知和行为产生长期影响。这些发现加剧了人们对社交媒体设计可能塑造心理过程（尤其是年轻用户）的日益增长的担忧。

## 2. 别吃Lady Gaga的奥利奥

**原文标题**: Stop Eating Lady Gaga's Oreos

**原文链接**: [https://www.experimental-history.com/p/stop-eating-lady-gagas-oreos](https://www.experimental-history.com/p/stop-eating-lady-gagas-oreos)

在这篇文章中，亚当·马斯特罗安尼对比了1990年代的反商业主义与当今对名人品牌产品的拥抱。在90年代，“向商业妥协”是种耻辱——珍珠果酱乐队拒绝拍摄音乐录影带以避免商业成功，反消费主义弥漫于整个文化。而今天，这种精神已消失殆尽：像Lady Gaga这样的艺人与奥利奥合作，粉丝们非但不批评，反而庆祝这类交易。

马斯特罗安尼将这一转变归因于两股力量。第一，“流行乐观主义”让评论家放弃了艺术品质的判断，而互联网使评论民主化，将普通消费者抬高到鉴赏家之上。这模糊了艺术与娱乐之间的界限，使毫无羞耻感的商业主义变得可接受。第二，“大逆转”：当通过向上流动致富变得更加困难时，通过注意力经济成名却变得更加容易。人们现在将自己视为“尚未成名的名人”，而非“暂时困窘的百万富翁”。这解释了为何亿万富翁遭人怨恨（只有19%的人认可杰夫·贝索斯），而像Lady Gaga这样的名人（61%的支持率）却备受爱戴——粉丝们感受到一条通往成名的共同路径，甚至将推广自己喜爱的明星视为推广自己。这助长了粉丝军团的行为和对公然贪婪的容忍。

马斯特罗安尼认为，解决方案是停止消费名人品牌产品，不再把名人视为与我们一样的人，并重新划定艺术与娱乐之间的界限。

## 3. 我本该喜欢生物学的

**原文标题**: I should have loved biology

**原文链接**: [https://jsomers.net/i-should-have-loved-biology/](https://jsomers.net/i-should-have-loved-biology/)

作者解释了他为何在中学时代未能爱上生物学：当时这门课被教成一门死气沉沉的事实背诵——名称、过程和公式——而没有传达出生命系统的奇妙。他认为，生物学只有通过提问和物理直觉来学习时才会引人入胜，而非死记硬背。

他引用了刘易斯·托马斯关于胚胎发育之奇妙的论述，并描述了自己在读完《哥德尔、艾舍尔、巴赫》之后，才真正将细胞理解为“递归式自我修改的程序”。他还强调奥斯瓦尔德·埃弗里的实验证明了DNA是“转化原理”，这正是那种学校教学中缺失的神秘与侦探故事。

作者批评教科书只呈现结论而不呈现问题，并倡导通过“薄而深”的切片式学习——比如能够组织理解力的编程项目。当他承担一篇关于SARS-CoV-2的杂志撰稿任务时，这一点变得清晰起来：尽管免疫学文献密集且分形般层层嵌套，他发现生物学和计算一样，有一个物理的底层。分子机器通过形状和结构运作，而非抽象的流程图。

他推荐了《生命的机器》和《计算机科学家的细胞生物学指南》等书，因为它们提供了视觉化、物理化的解释——蛋白质如何扩散、结合和识别信号。他还澄清了常见方法：离心、凝胶电泳、蛋白质印迹和荧光标记。最终，作者的核心观点是：生物学是一场理解生命物理机制的探索，它应当以这样的方式被教授——以惊奇、以问题、以可触可感的机制——而不是作为一份需要背诵的术语清单。

## 4. 我爱“厚”英语：致我英语老师们的道歉信

**原文标题**: I like 'em thick: an apology to my English teachers

**原文链接**: [https://www.experimental-history.com/p/i-like-em-thick](https://www.experimental-history.com/p/i-like-em-thick)

在《我喜欢“厚”的：向我的英语老师道歉》一文中，亚当·马斯楚安尼承认自己曾将“伟大”文学视为骗局，但现在相信艺术的“厚度”——即那些值得投入关注、越深入品味越能展现其深度的作品。

他用耶罗尼米斯·博斯的《人间乐园》来说明“厚度”。起初，他认为画中人物身上的那首著名的“屁股音乐”是个有趣的彩蛋。深入研究后发现，博斯是故意让它无法演奏：他将世俗音乐视为通往地狱之路，因此那奇怪的乐谱实际上是对永恒折磨的警告。这幅画在表面之下隐藏着层层深意。

马斯楚安尼指出了四种“增厚要素”：
1. **未走之路**——被舍弃的尝试留下的可见痕迹，比如葛饰北斋对同一图像的反复描绘。
2. **蛋糕粉里不放鸡蛋**——需要观众有所付出的艺术，如《第十一个小时》，它迫使读者重读以寻找隐藏线索。
3. **理由**——每个元素都有其用意，如《哈姆雷特》中反复出现的耳朵意象。
4. **血的牺牲**——需要付出真实时间或危险的艺术，诸如中世纪雕刻或佩恩·吉列特吞火。

他将“厚度”与“单薄”的、只有形式的作品进行对比：一本自助书籍的主张在审视下土崩瓦解，而简·雅各布斯的非虚构作品则提供几个精心挑选的事实，打开了整个充满洞见的世界。最终，厚度是区分艺术与纯粹物件的关键——而且发现它往往需要观者或读者自身的努力。

## 5. 速卖通运行无声WebAudio指纹识别，破坏蓝牙多点连接功能

**原文标题**: AliExpress runs silent WebAudio fingerprinting that breaks Bluetooth multipoint

**原文链接**: [https://blog.laserphile.com/2026/08/aliexpress-webpage-keeping-multipoint.html](https://blog.laserphile.com/2026/08/aliexpress-webpage-keeping-multipoint.html)

这篇文章描述了速卖通（AliExpress）首页如何静默运行基于WebAudio的指纹识别技术，这一技术干扰了作者的蓝牙多点连接耳机。耳机通常会在电脑和手机之间切换音频，但在Firefox或Chrome中加载速卖通页面后，手机音频会停止播放；关闭该标签页即可解决问题。

调查发现，页面中并没有传统的媒体元素或自动播放内容。相反，两个混淆过的阿里巴巴安全脚本——`collina.js`和`fireyejs.js`——创建了隐藏的`AudioContext`对象。这些上下文构建了一个音频图：锯齿波振荡器→AnalyserNode→ScriptProcessorNode→零增益GainNode→输出目标。增益为零，因此听不到任何声音，但该音频图仍然会被处理并连接到系统音频输出，从而保持蓝牙音频通道处于活动状态，阻止了多点切换功能。

这段音频代码是一个更大规模的浏览器指纹识别系统的一部分，该系统还利用画布（canvas）、WebGL、硬件信息、计时和交互数据。由于Cookie在跟踪方面并不可靠，这类指纹有助于区分人类用户和机器人，并防止欺诈行为，但与此同时，它们也会在静默状态下收集大量设备数据。

作者使用uBlock Origin并通过特定的过滤规则屏蔽了这两个脚本，从而阻止了隐藏的AudioContext的创建，同时没有破坏网站功能。屏蔽可能会引发额外的验证码，但确实解决了耳机问题。文章强调，这种实现方式会带来真实世界中的副作用：它运行在普通页面上，不可见，且无法通过常规浏览器控件静音，这展示了指纹识别技术如何无意间影响硬件行为。

## 6. Show HN：Huzzah——AI编程的新颖方法

**原文标题**: Show HN: Huzzah – a novel approach to coding with AI

**原文链接**: [https://www.danielvaughn.dev/posts/huzzah/](https://www.danielvaughn.dev/posts/huzzah/)

Huzzah是一位对AI编程代理感到沮丧的软件工程师开发的实验性编辑器。作者起初很喜欢编程代理，但逐渐厌倦了编写冗长、命令式、一次性的提示词。他发现的问题包括：没有可靠的人类意图记录、重复指令浪费token，以及自然语言对机器而言效率低下。

Huzzah提出了一种不同的范式：提示词即伪代码，采用声明式且持久化的方式。你不再需要聊天，而是编写一个`.hz`文件，其中包含简洁的伪代码。保存文件即生成真实代码；编辑文件（并保存）时，差异（diff）会被用作提示词，让LLM重新生成受影响的源代码。

示例包括fizz buzz（如`loop 100`、`modulo 3 ? "fizz"`）、购物车和待办事项列表的伪代码。其优点包括：更加简洁/易读、让使用者进入设计者思维模式、充当人工编写的文档，并且可以像CRDT一样做到与语言无关，支持多种目标。

注意事项：大规模场景下可能存在潜在问题；更适合新代码库而非现有代码库；对非专业人士来说，自然语言可能更容易上手；跨文件依赖更难处理；LSP功能需要额外生成。

Huzzah仍处于实验阶段，源代码和安装说明已在线提供。作者邀请大家试用并分享反馈。

## 7. HTML 也能做到

**原文标题**: HTML Can Do That

**原文链接**: [https://chrisburnell.com/html-can-do-that/](https://chrisburnell.com/html-can-do-that/)

克里斯·伯内尔的文章《HTML能做到》赞美了现代HTML如何处理以前需要JavaScript的动态功能。这篇文章为2026年HTML日而写，展示了多项原生特性，同时也指出了关于浏览器支持和可访问性缺口的重要注意事项。

**涵盖的关键特性：**

- **`popover`**：通过`popover`和`popovertarget`属性，原生支持轻触关闭、Esc键关闭和z-index管理。
- **`<dialog>`**：一个专门用于模态对话框的元素，可通过HTML打开/关闭（例如，通过`popover`或`<form method="dialog">`）。
- **分组`<details>`**：共享的`name`属性可创建互斥手风琴效果——打开一个会自动关闭其他项。
- **`command`与`commandfor`**：允许单独的按钮控制元素（例如，打开/关闭弹出框）而无需脚本。目前仅有少数命令稳定落地。
- **`loading="lazy"`**：将图片加载推迟到靠近视口时——无需IntersectionObserver。
- **`hidden="until-found"`**：片段链接自动显示隐藏部分，浏览器会移除该属性。
- **颜色/日期/范围输入**：浏览器内置的原生选择器，但作者警告这些控件感觉尚未完成，存在样式不一致和可访问性差的问题。
- **`<datalist>`**：提供原生自动补全建议，但各输入类型的支持仍然参差不齐，实现问题持续存在。

**重要注意事项：**伯内尔强调，尽管这些特性令人兴奋，但浏览器实现往往严重欠缺，且无法满足可访问性需求。他建议对表单元素和datalist保持谨慎，链接到Adrian Roselli的comboboxen研究，并敦促读者不要用该页面来向老板证明决策的合理性——提醒大家用户的上网方式各不相同，可访问性必须始终是优先事项。

## 9. Linux 7.2

**原文标题**: Linux 7.2

**原文链接**: [https://www.igalia.com/2026/08/19/Linux-72-Released.html](https://www.igalia.com/2026/08/19/Linux-72-Released.html)

Linux 7.2 于 2026 年 8 月 19 日发布，被称为有史以来第二繁忙的内核周期，仅次于 6.7。主要内核改进包括缓存感知调度、MGLRU 增强、为 sched_ext 引入子调度器，以及自动多尺寸透明大页。

Igalia 贡献突出，尤其是在 DRM 和 GPU 方面。他们计划的 DRM 调度器公平策略旨在改善 GPU 共享和交互性能，但在最后一刻出现回归后被回退到旧的 FIFO 调度器；该策略仍作为实验性可选项提供，已知修复预计将在未来版本中发布。

在 sched_ext 中，Igalia 改进了可观测性，确保触发调度器故障的 CPU 首先被转储，并将其 ID 暴露给 BPF 调度器和用户空间工具。他们还为树莓派 4 和 5 的 GPU 添加了运行时电源管理，仅在活动时为 V3D GPU 供电，从而降低了空闲功耗。通过修正 tile 内存处理，修复了影响 RetroPie 用户的长期存在的树莓派 3 GPU 崩溃问题。此外还完成了额外的树莓派 GPU 重置修复。

该团队帮助解决了一个存在 14 年之久的 futex 健壮列表导致数据损坏的 bug，修复了 ueagle-atm 驱动中的竞态条件，并改进了 x86 启动时的 memcmp() 内联汇编。最后，基于 Igalia 的 Rodrigo Siqueira 最初完成的工作，amdgpu 驱动对 HDMI 2.1 固定速率链路（FRL）的初步支持已被合并。

该周期包含 Igalia 编写的 82 个补丁、审阅的 74 个补丁和 13 个 acked 贡献。

## 11. Show HN：我训练了一个1.25亿参数的模型，在设备端实现钢琴音乐自动续写

**原文标题**: Show HN: I trained a 125M model to autocomplete piano on-device

**原文链接**: [https://simedw.com/2026/08/20/midi-autocomplete/](https://simedw.com/2026/08/20/midi-autocomplete/)

这篇文章描述了一个设备端 AI 钢琴自动补全系统的构建，类似钢琴版的 GitHub Copilot。最终模型是一个 1.25 亿参数的 Transformer，在 iPhone 15 上每秒可处理约 108 个音符，并集成在免费应用 RollTab 中。

关键突破来自：

- **MIDI 表示**：没有将单个 MIDI 事件（音符开/关）进行词元化，也没有使用多词元音符属性，而是将每个音符表示为单个词元，包含五个类别字段：音高、增量起始时间、时值和力度。和弦使用 delta=0。这避免了音符关闭漂移，并将自回归步骤减少到每个音符一步。
- **数据清洗**：一个由数十万份钢琴 MIDI 文件（约 3 亿个音符）组成的精选数据集，胜过了一个大 5 倍但噪声更多的数据集。
- **DPO 后训练**：使用来自 Gemini 评估的成对偏好数据进行直接偏好优化。使用 β=0.03 的共识过滤数据集效果最佳，69% 的续写比基础模型更受偏好。

其他值得注意的要点：

- 在音符字段之间进行计划采样提升了 rollout 质量，尽管它增加了验证损失。

## 12. SpacetimeDB：技术简评

**原文标题**: SpacetimeDB: A Short Technical Review

**原文链接**: [https://strn.cat/posts/spacetime/](https://strn.cat/posts/spacetime/)

SpacetimeDB v2 是一个数据库，它还使用 WebAssembly reducers 在数据库内部运行应用程序代码。文章批评了其发布营销：一个嘲讽竞争对手的恶搞式视频，以及在技术上具有误导性的基准测试。

基准测试之所以看起来令人印象深刻，主要是因为应用程序逻辑在内存中执行，紧邻数据，避免了网络往返——而不是因为该数据库本质上比传统分布式系统更快。作者将此比作他在 PlanetScale 任职期间所避免的不公平基准比较。

在底层，存储引擎本质上是一个由单个全局读写互斥锁保护的内存哈希表。所有写入操作完全串行化，甚至在写入执行期间读取也会被阻塞。Reducers 在临界区内运行任意用户代码，因此它们无法发起 HTTP 调用。测试版“Procedures”允许执行开销较大的工作，但开启事务会获取全局锁，可能导致整个系统停滞。

持久性较弱：预写日志每 50 毫秒异步刷新一次，而不是作为事务的一部分。“withConfirmedReads”选项会强制服务器等待最多 50 毫秒，直到数据写入磁盘。文章将此与早期的 MongoDB 进行比较，警告此类捷径可能会损害长期声誉。

主要的权衡取舍：SpacetimeDB 不是分布式系统。它有一个主实例和最终一致的从节点，一切都受限于单台机器的 CPU 和内存。数据必须完全驻留在内存中；否则，数据库将无法运行。该设计更适合定位为“更强大的 Redis”，而不是关系型数据库的竞争者。

最初的用例是 MMORPG 后端，在这种场景下异步持久性是可以接受的。转向更广泛的企业市场是可以理解的，但作者认为，诚实的技术文档比“疯狂的基准测试”和对竞争对手的嘲讽更能让产品受益。

## 17. DiffusionGemma 技术报告

**原文标题**: DiffusionGemma Technical Report

**原文链接**: [https://arxiv.org/abs/2608.00146](https://arxiv.org/abs/2608.00146)

DiffusionGemma 是一种实验性的开放权重语言模型，它使用离散扩散（discrete diffusion）而非标准自回归（AR）解码来生成文本。它不是一次生成一个 token，而是并行迭代地细化 256 个 token 的块，从而消除了传统 LLM 的顺序瓶颈，实现了极高的生成速度。

该模型通过对混合专家（mixture-of-experts）Gemma 4 模型进行微调获得，该模型具有 38 亿激活参数和 252 亿总参数。这种微调在计算上很高效：其两阶段流程使用的训练 token 预算不到原始 AR 模型训练预算的 10%。第一阶段应用监督微调来教导双向去噪；第二阶段将强化学习与采样器蒸馏相结合，以同时提高输出质量和推理效率。

主要结果：DiffusionGemma 在生成速度和能力之间的权衡中建立了新的帕累托前沿。在其评估套件中，它每次前向传播生成约 20 个 token，在单块 NVIDIA H100 GPU 上每秒可达到约 1500 个输出 token——即使使用最先进的推测解码，也远快于 AR 模型。

该模型还保留了原始 Gemma 4 的有用能力，包括思考模式、多模态输入支持和长上下文处理。尽管基于扩散的训练，它仍然能够进行 AR 生成，仅性能损失很小，这表明未来模型朝着混合扩散-AR 解码的方向发展是一条有前途的路径。

**原文链接**: [https://dominik.info/blog/go-generic-methods](https://dominik.info/blog/go-generic-methods)

Go 1.27 移除了 Go 1.18 泛型中一个长期存在的限制：方法现在可以定义自己的类型参数，而无需依赖接收者的结构体类型。

以前，如果你有一个 `Node[T any]`，并且想要一个将值转换为另一种类型 `U` 的 `Map` 方法，你必须将 `U` 添加到结构体本身：`Node[T, U]`。这迫使所有其他方法都携带一个未使用的类型参数，这是糟糕的设计。解决办法是将此类操作改为包级函数，因为函数本身已经可以拥有自己的类型参数。

这一延迟源于 Go 对泛型的实现方式。编译器使用单态化，在编译时生成泛型代码的具体副本。然而，Go 的接口系统在运行时动态解析值。泛型方法并不完全适合这种模型：在检查某个类型是否实现某个接口时，编译器需要考虑泛型方法多到难以计数的可能实例化。反射也可以在运行时调用方法，这使得编译期实例化跟踪变得困难。

因此，Go 团队决定：泛型方法允许定义在具体类型上，但不能成为接口定义的一部分。泛型方法同样不满足可能匹配的接口方法。这样既保持了接口分发的可控性，又在具体类型上实现了灵活的方法级泛型。

文章最后附上了 Go 1.27 发布说明、原始提案以及关于泛型性能讨论的链接。

## 24. Git 任意规模

**原文标题**: Git at any scale

**原文链接**: [https://cursor.com/blog/git-at-any-scale](https://cursor.com/blog/git-at-any-scale)

大规模托管 Git 仓库极其困难，根源在于 Git 的分布式设计：所有仓库实例完全相同，数据以 packfile 格式存储并传输。packfile 是大型二进制文件，随机遍历特性使分布式文件系统方案（NFS、DRBD 等）性能极差。GitHub 的 Spokes 方案成为行业标准：在本地 NVMe 上存储原生仓库，在 packfile 层面复制，并通过三阶段提交保证所有副本完全一致。但 Spokes 存在扩展性瓶颈——副本越多，推送吞吐量越低；同时每个副本都是“宠物”，需要精确的路由表和持续维护。

作者在 Cursor 开发的 Continuity 系统提出了新思路：以 S3 对象存储中的预写日志（WAL）为唯一事实来源，本地 Git 仓库仅是热缓存。推送先持久化为 WAL 条目，通过 S3 原子 CAS 同步，确认前保证写入完成。系统无状态，无需路由表或共识选举，任意服务器可处理推送；副本通过 UDP gossip 快速追赶，读取时用 S3 条件 GET 验证一致性。压缩仅由主节点执行，结果写入 WAL，副本跟随下载。这让副本数量可自由伸缩：大型 monorepo 可扩展到上百副本，空闲小型仓库甚至可回收，从 WAL 按需还原。

对比 Azure DevOps 用关系型数据库存引用，Continuity 坚持不依赖外部数据库，因为 Git 数据一致性至关重要。WAL 提供完整审计溯源，可精确恢复任何状态。作者最终推出 Origin 平台，强调可靠性和一致性，并承诺为客户提供顺畅迁移路径。

## 25. GitHub、自动伸缩与组件替换谬误

**原文标题**: GitHub, autoscaling, and the component substitution fallacy

**原文链接**: [https://surfingcomplexity.blog/2026/08/19/github-autoscaling-and-the-component-substitution-fallacy/](https://surfingcomplexity.blog/2026/08/19/github-autoscaling-and-the-component-substitution-fallacy/)

这篇文章讨论了由错误配置的自动扩缩容策略导致的一次 GitHub 故障。问题涉及一个 Istio sidecar Pod 达到并发限制，但自动扩缩容策略监控的是主机服务的指标，而非 sidecar 的限制，从而未能正确扩容。

作者解释了自动扩缩容的基础：服务根据负载指标（通常是 CPU 利用率）进行扩容，但 CPU 可能很低而服务已经饱和（例如，线程阻塞在 I/O 上）。有效的自动扩缩容策略因服务而异，需要仔细选择指标并进行负载测试。服务所有者往往不是自动扩缩容专家，很容易错误配置它们。

然而，作者警告不要只关注有缺陷的组件——David Woods 所称的“组件替代谬误”。系统总是充满潜在缺陷，但它们并不会持续故障，这意味着组件之间的交互比单个故障更重要。在此次事件中，因素包括变化的流量模式、自动扩缩容策略、Istio sidecar 饱和、重试逻辑、HAProxy 节点饱和以及认证流量。

作者还指出，公开的事故报告缺乏深度，并鼓励读者在内部的事故后复盘中提出更深层次的问题：策略历史、流量特征以及流量增加的原因。
